# pc-07 — Which part is MAIN: an H8SX/1668R-group MCU, not the H8S/2456

Lane 7 of the PC-software pass. This lane closes residual #4 in `RESUME-DEEP.md`, the exact MAIN part.
The work is static analysis of files on disk. Nothing was written to a radio. `Firmware\`, `decrypted\`
and every existing IDA database are unchanged. No new IDA database was needed: the register inventory
reuses the existing MAIN-FULL outputs `ida\out\main-full\ioregs.tsv` (16,893 access sites) and
`absrefs.tsv`. The only other input is plain Python over `decrypted\FT3D_MAIN_ver102_EXP.bin`.

## Verdict

**MAIN is a Renesas H8SX/1668R-group MCU: R5F61668R (1 MB flash, 56 KB RAM), or its LVD/POR twin,
the R5F61668M.** The group comes in LQFP-144 and LFBGA-176 packages. The core is an **H8SX**, not an
H8S/2600. It runs H8S object code, so IDA's `h8s300a` disassembly is still valid.

| Rank | Candidate | Verdict | Discriminating evidence |
| --- | --- | --- | --- |
| **1** | **H8SX/1668R — R5F61668R** (1024 KB / 56 KB) | **Best match** | All 214 in-map register addresses the image touches exist, with the functions the code uses. All 30 occupied vector slots map to the matching sources. The RAM base `0xFEE000` and the 1 MB image size match the only 1 MB / 56 KB member. |
| 1= | H8SX/1668M — R5F61668M | Cannot be separated from 1668R | This is the same manual and the same map, plus LVD/POR (`LVDCR 0xFFFE78`, vector 78). The image never touches `LVDCR` or `RSTSR`, and vector 78 is a filler slot, so the 1668R is slightly preferred. That is weak evidence. |
| 2 | H8SX/1658R / 1658M (120-pin, 1 MB / 56 KB) | **Excluded** | The 120-pin die has **no port 3 and no port C**. The image drives `P3DR 0xFFFF52` (29 code accesses, the DSP reset/boot line in doc-09), `PCDR 0xFFFF5B` (33), and also `P3DDR`, `PCDDR` and `PORT3`. |
| 3 | H8SX/1664R, 1663R, 1665, 1655 | Excluded | 40 KB RAM starting at `0xFF2000`, and ≤ 512 KB flash. The image zero-fills RAM from `0xFEE000` (`0x2138`), has 103 references in `0xFEE000`–`0xFF1FFF`, and enables RAM 6/5 in `MSTPCRC` (`0x21EA`). |

**Corrections to earlier notes:**

- `04-main-recovery.md` §11 named the "H8S/2456 group". That is wrong for the reasons in the table above.
- `docs\compiler.md` named "H8S/2370". The compiler identification (Renesas H8S/H8SX C compiler) still stands.
- Doc-04 §2 described an SCI-A `BRR = 0x00` (500 kbaud) path in `sub_45186`. That path is not present. The two paths write `BRR = table[FF8C27]` or `BRR = 0x0C` (see §5). 500 kbaud belongs to SCI_6 only.

## 3. USB Function Module

The block is the H8SX/1668R USB 2.0 full-speed function module at `0xFFEE00`. Its layout is EP0
control (8 bytes), EP1 bulk-out (64), EP2 bulk-in (64) and EP3 interrupt-in (8), and it needs a
48 MHz `cku` clock. It is a different block and address from the H8S/2456 USB at `0xFFFB00`.

Facts the PC side can use:

- **`DMA` register (`0xFFEE2D`) bit 2 is `PULLUP_E`**, the D+ pull-up drive on pin PM4. `bset #2` at
  `0x54CA6`, `0x78154` and `0x78216` is the soft-attach, so the radio appears on the bus at that point.
  `bclr` at `0x27B0` (NMI) and `0x3EC52` detaches.
- `CTLR` (`0xFFEE2F`) `0x08` is `RSME`, a remote-wakeup resume request. Vector 238 is the USB resume interrupt.
- `EPIR` (`0xFFEE32`) takes the 50-byte endpoint-information image from `0x54C12`.
- `FCLR = 0x73` clears the FIFOs.

**Boot mode** (manual §25.8), shown for reference only; nothing here should be exercised on the radio:

| Mode | Pin setting | Channel | What the boot ROM does |
| --- | --- | --- | --- |
| USB boot | `MD3-0 = 0010`, `PM2 = 1` | On-chip USB, EP1 bulk-out 64 / EP2 bulk-in 64 | Enumerates with the Renesas boot ROM descriptors. This matches the updater's `Generic Boot USB Direct`, VID `0x045B` (Renesas) PID `0x0025`. The boot ROM answers inquiries, **erases the whole user MAT automatically**, then accepts program, sum-check, blank-check and user-MAT read commands. |
| SCI boot | Same, with `PM2 = 0` | **SCI_4 on P60/TxD4, P61/RxD4**, the same pins as the DATA-jack CAT port | Auto-baud from `0x00` bytes. It supports 9,600 or 19,200 bps at a system clock of 8–18 MHz. |

These modes are silicon features, consistent with the ver 1.02 updater path and with the "program
switch selected in silicon" finding. They do not identify the part, because the H8S/2456 also has USB
boot, but they are consistent with it.

## 4. Clock — EXTAL 16 MHz, MD_CLK = 1, I = P = B = 16 MHz, USB 48 MHz

At the reset path, `sub_20FA` writes `SCKCR = 0x0111` (`0x20FC`/`0x2100`). The warm path `sub_24B6`
writes it at `0x24CC` and the NMI path at `0x282C`. That value sets ICK = PCK = BCK = `001`.

The H8SX/1668R clock tree (Table 27.1) has two possible settings:

| MD_CLK | Divider for `001` | USB clock `cku` | EXTAL needed for 48 MHz USB | Resulting Pφ |
| --- | --- | --- | --- | --- |
| 0 | EXTAL × 2 | EXTAL × 4 | 12 MHz | 24 MHz |
| **1** | EXTAL × 1 | EXTAL × 3 | **16 MHz** | **16 MHz** |

MD_CLK = 0 would put the SCI_4 BRR table below on non-standard rates (57.7k, 7.2k, …). MD_CLK = 1 with
a 16 MHz crystal gives exactly the four standard rates at +0.16%, which doc-04 and doc-05 already
measured. So the clocks are:

- **EXTAL = 16 MHz, MD_CLK = 1.**
- **Iφ = Pφ = Bφ = 16 MHz.**
- **cku = 48 MHz.**

This is Inferred (strong): it is the only self-consistent solution. It also sits inside the SCI-boot
auto-baud window of 8–18 MHz.

## 5. SCI channels and baud-rate formula

The H8SX SCI in asynchronous mode gives

B = Pφ / (64 · 2^(2n−1) · (N+1))

For `SMR.CKS = 0` (n = 0) this is **B = Pφ / (32 · (N+1)) = 500,000 / (N+1)** at 16 MHz. `SEMR`
(`ABCS`/`BGDM`) is never written: there are no accesses to `SEMR_2 0xFFFE84` or `SEMR_6 0xFFF618`, so
16× oversampling applies.

| Doc name | H8SX channel | Registers | Pins | Vectors | TX path | Mode / BRR | Rate |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **SCI-A (DATA jack)** | **SCI_4** | `FFFE90`–`95` | P60 TxD4 / P61 RxD4 | 160-162 | IRQ or DMAC ch2 (`DMRSR_2 = TXI4`) | Async 8N1. `BRR = {0x67, 0x33, 0x19, 0x0C}[0xFF8C27]`, table at `0x452C2`, write at `0x451AE`. Fixed `0x0C` when `0xFF8DDE ≠ 0` (`0x451F4`–`0x45208`, `sub_734C2` at `0x734D6`). `0x19` in `sub_73540` (`0x73554`). | **4800 / 9600 / 19200 / 38400** (menu `COM PORT SETTING`, +0.16%). The framed clone/PC personality is fixed at **38400**. `sub_73540` uses 19200. |
| SCI-B | SCI_2 | `FFFF60`–`66` | P10/P11 | 152-154 | IRQ | Async 8N1, `0x0C` | 38400 |
| SCI-C (DSP) | SCI_1 | `FFFF88`–`8D` | P26/P25 (+SCK1) | 148-150 | DMAC ch1 (`TXI1`) | Clocked sync per doc-05 | External clock |
| SCI-D (SUB IPC) | SCI_6 | `FFF610`–`615` | PM0/PM1 | 224-226 | DMAC ch0 (`TXI6`) | Async 8N1, `0x00` | **500,000** exactly |

**DATA-jack PC settings:** 8N1, no flow control, at 4800, 9600, 19200 or 38400 as set in the radio's
COM PORT SETTING menu. The clone/PC-link personality runs at 38400. The +0.16% clock error is far inside
any USB-UART's tolerance.

## 7. Why the core is H8SX, and what that changes

The DMAC register geometry, `DMRSR` taking vector numbers, `SCKCR`/`MSTPCRA-C` at `0xFFFDC4`–`0xFFFDCC`,
`TSTR` at `0xFFFFBC`, and the 256-slot vector numbering are all H8SX/1600 features. The code decodes
cleanly as H8S/2600 because the Renesas compiler was evidently run for an H8S-compatible CPU type, and
H8SX is object-code upward compatible. That is consistent with the `stm/ldm` register-window idiom in
`compiler.md`. For tooling this means:

- Keep IDA on `h8s300a`, but use the H8SX/1668R register names (the TSV column `H8SX1668R_name`).
- Any H8SX-only opcode would show up as an undecoded gap. None was reported in doc-04's 3,899-function
  coverage. That was not re-scanned in this lane.

## 8. Open items and anomalies

- **`0xFFFF6B` write.** `sub_20FA` writes `0x03` at `0x2352`, just before `DADR1`/`DADR0 = 0x7F`. The
  address is not in the H8SX/1668R register list; `DACR01` is at `0xFFFF6A`. This is the single genuine
  code access outside the map. It is probably template init code that is harmless on this die. It does
  not favour any other candidate.
- **1668R vs 1668M** cannot be separated from the image. The package (FP LQFP-144 or BG LFBGA-176) and
  temperature grade (N/D) cannot be told either. The chip marking on the MAIN board would settle it.
- The `code_hits` filter is heuristic. Register rows with `code_hits = 0` and no note are data
  mis-decodes. Rows with a note were checked by hand.

## Method and reproduction

1. **Register accesses.** `ioregs.tsv` and `absrefs.tsv` (MAIN-FULL job). Byte context comes from the
   plaintext image.
2. **Datasheets.** Public Renesas hardware manuals, converted locally with `pdftotext -layout`. The
   manual files are not stored in the workspace.
   - H8SX/1668R-1668M, REJ09B0412-0200: Table 7.2 vectors, §20 USB, §24 RAM, §25.8 boot modes, §27 CPG, §28 module stop, §29.1 register list.
   - H8SX/1658R-1658M, REJ09B0413-0200: §13 ports, §28.1.
   - H8S/2456-2456R-2454, R01UH0309EJ0500: Table 1.2 products, §25.1, vector table.
   - Renesas USB device catalogue (2009.10), for the ROM/RAM line-up of H8SX/1665, 1663, 1664, 1658 and H8S/2215, 2218, 2212.
3. **Regenerate the table:** `python ida\jobs\pc_l7_regmatch.py <dir with h8sx1668r.txt, h8sx1658r.txt, h8s2456.txt>`.
