# N5 — the 52 B tail 0x0771AE–0x0771E1 (MAIN)

Lane N5. Owner-side static analysis of files on disk (MAIN `decrypted\FT3D_MAIN_ver102_EXP.bin`,
sha256 `8e3ecd05…`, SUB `b93570b3…`; both re-checked at the start of the lane and again at the end,
unchanged). H8SX, big-endian, base 0, so file offset = address. Nothing written, flashed or
transmitted. Seed DB `M1_MAIN_FINAL6` copied to private DB `N5_TAIL52`; no shared or other-lane DB
opened.

## Verdict

**Not found — no edge of any kind reaches 0x0771AE–0x0771E1 (52 B), whole MAIN image.** The three
previously-unscanned edge classes my lane was asked to re-check — relative branches (rel8/rel16),
`@@aa:8` memory-indirect, and fall-through from the previous instruction — add nothing to M7's
negative result. The byte-sweep for rel8 branches produced three apparent inbound branches
(`0x077142`, `0x077158`, `0x077161`); all three are **mid-instruction false positives**, confirmed
against the seed's instruction boundaries. The instruction immediately before the tail,
`0x0771AC 54 02 rts/l er2`, is a **return**, so there is no fall-through. The block entry `0x0771AE`
has zero code refs and zero data refs. The 52 B are a self-contained orphan block (a register-renamed
near-duplicate of `sub_7711E`'s ring-enqueue code plus a short spin-wait), already named, ending in
`rts` at `0x0771E0`. They are **named-not-proven dead code**. **Proven delta = 0.** Named delta = 0
(already named; confirmed by the M-wave ledger). No correction to any earlier doc: this confirms
doc 119 (M7) and `ida\out\m-wave-recon\README.md`.

## Method

What I ran, and the scope:

1. **Whole-image conservative edge scan** (`ida\out\tail-52\n5_edge_scan.py`, pure Python over all
   1,048,576 bytes, every byte offset, instruction boundaries ignored — deliberately
   over-inclusive). Five edge classes, each targeting any address in `[0x0771AE, 0x0771E1]`:
   - rel8 `Bcc`/`BRA` (`0x40`–`0x4F`) and `BSR` (`0x55`): target = `addr+2 + sign8(disp)`;
   - rel16 `Bcc`/`BRA` (`0x58 x0 dddd`) and `BSR` (`0x5C 00 dddd`): target = `addr+4 + sign16(disp)`;
   - abs24 `JMP @aa:24` (`0x5A`) / `JSR @aa:24` (`0x5E`);
   - any BE32 value anywhere equal to an even address in range (covers pointer tables,
     `mov.l #imm` immediates, and `@@aa:8` vector slots);
   - `@@aa:8` `JMP`/`JSR` (`0x5B`/`0x5F`): the page-0 vector it reads, resolved and range-checked.
2. **Authoritative decode** from the `M1_MAIN_FINAL6` seed (`ida\jobs\n5_tail.py`, DB `N5_TAIL52`):
   linear decode of `0x077100`–`0x0771F2`; `get_item_head`/`is_code` for each byte-sweep candidate;
   `XrefsTo` for **every** address `0x0771AE`–`0x0771E1`; `CodeRefsTo(flow=1)` and `DataRefsTo` for
   the block entry `0x0771AE`.

Scope covered: the complete MAIN image for the five edge classes above, plus the seed's full xref
graph into every byte of the range. What I did not do: I did not re-derive the FINAL7 masks (not in
scope), and I did not open any shared DB. abs16 (`@aa:16`) was not scanned because `0x0771AE` lies
outside both abs16 windows (`0x000000`–`0x007FFF`, `0xFF8000`–`0xFFFFFF`) and is therefore not
addressable by an abs16 operand at all — a structural impossibility, not a gap.

## Findings

**Layout.** The seed places the tail between two functions, inside neither:
`sub_7711E` = `[0x07711E, 0x0771AE)` and `sub_771E2` = `[0x0771E2, 0x07720E)`. IDA reports **no
function** at `0x0771AE`. (Confirmed, `ida\out\tail-52\n5_ida.txt`.)

**The pre-tail instruction is a return — no fall-through.** (Confirmed.)

    0771A6  01 00 69 92   mov.l   er2, @er1
    0771AA  28 8a         mov.b   @0x8A:8, r0l
    0771AC  54 02         rts/l   er2        <- last insn of sub_7711E; RETURN
    0771AE  01 00 6d f2   push.l  er2        <- TAIL entry

**The three rel8 byte-sweep candidates are all mid-instruction false positives.** (Confirmed, via
`get_item_head`.)

| sweep src | sweep claim | real owning instruction (head) | reality |
| --- | --- | --- | --- |
| `0x077142` | `40 70` BRA→`0x0771B4` | `0x077140 01 5d 40 70 fd 62` `mov.w #0x70,@0xFFFFFD62:16` | `40 70` is the immediate `#0x70` + operand; src not a head |
| `0x077158` | `40 60` BRA→`0x0771BA` | `0x077156 01 5d 40 60 fd 62` `mov.w #0x60,@0xFFFFFD62:16` | `40 60` is the immediate `#0x60` + operand; src not a head |
| `0x077161` | `48 73` BVC→`0x0771D6` | `0x077160 40 48` `bra loc_771AA:8` | `0x077161` is the BRA displacement byte; src not a head |

The genuine `BRA`s in `sub_7711E` (`0x07712C` beq, `0x077130` bne→`0x0771AA`, `0x07714A`/`0x077160`/
`0x077170` bra→`0x0771AA`, `0x0771A0` bra→`0x0771AA`) all land on `0x0771AA` or earlier — none enters
the tail.

**The other two sweep hits are intra-block.** `0x0771C4 45 06 bcs loc_771CC` and
`0x0771D8 4a fc bpl loc_771D6` both branch **within** the 52 B (targets `0x0771CC` and `0x0771D6`).
Not inbound edges. (Confirmed.)

**No inbound xref of any kind.** `XrefsTo` across `0x0771AE`–`0x0771E1` returns only `type=21`
(ordinary flow from the previous byte inside the block) and `type=19` (the two intra-block
conditional jumps above). `0x0771AE` itself appears in no `XrefsTo` list; `CodeRefsTo(0x0771AE,
flow=1) = []` and `DataRefsTo(0x0771AE) = []`. (Confirmed.)

**No abs24, no BE32, no `@@aa:8`.** The whole-image scan found zero `JMP/JSR @aa:24` into range, zero
BE32 value (anywhere, including page-0 vectors and `mov.l #imm` immediates) equal to any even address
in range, and zero `@@aa:8` vector resolving into range. So no "helper / er1 dispatch" edge exists:
the constant `0x000771AE` (or any other in-range address) is never loaded as an immediate, and no
pointer table holds it. This reproduces M7's result and extends it to the relative-branch and
indirect classes. (Confirmed; `n5_edge_scan.py`, 0 hits in those four classes.)

**What the 52 B are.** `0x0771AE`–`0x0771D4` is a register-renamed near-duplicate of `sub_7711E`'s
ring-enqueue body (`0x077182`–`0x0771AC`): it enqueues one byte into a ring whose base is passed in
`er0` (the live copy hardcodes the IN-ring base `0xFF62C8`). `0x0771D6`–`0x0771E0` is a short
spin-wait (`bpl` on bit 7 of `@0x8C:8`) then a store and `bclr`, ending `0x0771E0 54 70 rts`. The
shape is a would-be generic `ring_enqueue(er0)` helper plus a TX-ready wait, left unlinked — no call
site was ever emitted. (Inferred from the byte-identical structure; the duplication itself is
Confirmed.)

## USB relevance

None beyond confirming the existing picture. These 52 B sit in MAIN's CDC-ACM service-window code
region (the SCI-C ↔ USB RX bridge neighbourhood, doc 119), but they are unreachable dead code: they
add no USB surface, expose no new endpoint or handler, and carry no sample path. The live CDC bridge
(`sub_7711E` and the ISR-walked handler records) is unchanged by this finding. Mission answers Q1/Q2/
Q3 are untouched.

## Open

1. Nothing actionable for reachability — the range is closed as dead. The only residual question is
   cosmetic: whether a future FINAL8 seed should keep these 52 B *named* (current ledger choice) or
   additionally tag them as an identified-but-unlinked `ring_enqueue(er0)` helper for the owner's
   reading convenience. No byte or mask changes either way.
2. The adjacent, still-open item from doc 119 (the ~300 B near-duplicate EP0 handlers
   `0x076ADE`–`0x076C09`) is the same *phenomenon* — compiler-emitted duplicate/spare routines with no
   reference — and would be the higher-value next target in this neighbourhood. Out of this lane's
   range.
