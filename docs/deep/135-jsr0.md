# 135 — N8: what RAM address 0 holds for the live `jsr 0` (SUB)

Owner-side static analysis of the owner's own FT3DR/FT3DE ver 1.02 SUB firmware, file already on
disk. Read-only: no database beyond a private seed copy, no image or published mask modified,
nothing written, flashed, or transmitted to any radio. SUB sha256
`b93570b3c2f69ccb51c113c893b4bc4c414cf78ceddde478748404e0768c6230`, unchanged at start and end of the
lane. MAIN sha256 `8e3ecd05…`, unchanged (not touched by this lane).

Model: claude-opus-5-5.

## Verdict

The two `jsr` sites doc 127 flagged (`FFEE2220`, `FFEE223B`, bytes `66 03 7f 13` =
`mov.l #0, r3 ; jsr r3`) jump through register **R3**, whose only writer on the path is the
immediate `#0` at the site itself — there is **no memory source** for the target register. The
effective jump target is RAM **address `0x00000000`**.

**No code in the SUB package ever stores a value at RAM address `0x0`** — Confirmed at whole-image
coverage. CC-RX startup does not initialise it: the `.data` copy table (DTBL) has no range covering
`0x0-0x3`, and the BSS-clear table (BTBL) begins at `0x4`, so `0x0-0x3` is the one 4-byte hole at the
base of on-chip RAM that is neither copied nor zeroed. The value present at `RAM[0]` is therefore the
RX64M power-on-indeterminate state; the firmware never places code or a pointer there. **A `jsr` to
`0` lands in uninitialised RAM — a deliberate fault/trap, not a reachable call target.** The jump
target value is **Unknown** (not determined by the package), which is the correct and useful answer.

**Refinement of doc 127 (not a reopen of closed work):** neither site is on a *live* path. In the
sanctioned seed `K7_SUB_FINAL3`, every call path above both sites roots in a function the seed marks
dead (`FFEE1780`, `FFEE1868`, `FFEE19E4`) with 0 inbound edges, 0 vectors, and 0 pointer hits. The two
functions are CC-RX standard-library low-level character I/O (`charput`-style) and its callers
(`_write`/`printf` family), linked but never called by the application.

Named delta **0**. Proven delta **0**. (These bytes are already code inside the M15 SUB window; this
lane types no byte that is unset in a named mask.)

## Method

- SUB base `0xFFC00000`, little-endian, file offset = addr − base. RX immediate `66 0N` =
  `mov.l #0, rN` (short uimm4 form); `7f 1N` = `jsr rN`.
- IDA 9.1 through `ida\run_job.py` only, private DB `N8_JSR0_SUB` seeded `--copy-from`
  `ida\db\jobs\K7_SUB_FINAL3\K7_SUB_FINAL3.i64`; later passes `--reopen`. Jobs
  `ida\jobs\n8_jsr0_sub.py`, `n8_jsr0_callers.py`, `n8_jsr0_up.py`. No other DB opened.
- Disassembled both enclosing functions; enumerated xrefs to each site, to each function start, and to
  RAM addresses `0`/`1`/`2`/`3`; walked the call graph above both sites to a fixpoint; decoded the
  DTBL/BTBL and the EXTB (32) and INTB (256) vector tables.
- Independent whole-image byte scans (Python, `bytes`-based): the store-through-zero-base idiom
  (`66 0N` then register-indirect store `C3`/`CB`/`E3` with base == N), and every 32-bit LE dword
  equal to any function entry in the chain (pointer/vector search).
- Every citation re-asserted against the image by `ida\out\jsr0\bytecheck.py` (12/12 PASS, including
  the SUB sha256).

## Findings

**1. The two sites load the constant 0, no memory source (Confirmed).**
`FFEE2220 66 03 7f 13` and `FFEE223B 66 03 7f 13`. R3 is set to `0` by the immediate immediately before
each `jsr r3`; byte-verified. Doc 127's reading is correct.

**2. The enclosing functions (Confirmed).** Clean linear disassembly from the seed DB:

    sub_FFEE2208 (FFEE2208..FFEE2224):          sub_FFEE2225 (FFEE2225..FFEE2247):
      FFEE2208 fb22238c0000 mov.l #8C23h,r2       FFEE2225 fb1200002101 mov.l #1210000h,r1
      FFEE220E c321         mov.b r1,[r2]          FFEE222B fb22238c0000 mov.l #8C23h,r2
      FFEE2210 fb1200002201 mov.l #1220000h,r1     FFEE2231 fb3264d20100 mov.l #1D264h,r3
      FFEE2216 fb3264d20100 mov.l #1D264h,r3       FFEE2237 e332         mov.l r2,[r3]
      FFEE221C e332         mov.l r2,[r3]          FFEE2239 ef32         mov.l r3,r2
      FFEE221E ef32         mov.l r3,r2            FFEE223B 6603 7f13    mov.l #0,r3 ; jsr r3
      FFEE2220 6603 7f13    mov.l #0,r3 ; jsr r3   FFEE223F fb22238c0000 mov.l #8C23h,r2
      FFEE2224 02           rts                    FFEE2245 5821         movu.b [r2],r1
                                                   FFEE2247 02           rts

Both set up a RAM pointer in `r2` (= `0x1D264`) as the call argument, then call address `0`. The
stores they make are to RAM `0x8C23` and `0x1D264` — **not** to address `0`. `0x8C23` and `0x1D264`
lie inside the BTBL-cleared BSS region (`0x4-0x1217E`). `0x01210000`/`0x01220000` are magic/command
constants, not addresses in the RAM range (RAM content ends at `0x698FC`). The shape — pointer arg
plus an indirect call whose target constant-folded to `0` — is a CC-RX low-level stdio byte-I/O stub
whose device hook was never provided in this build.

**3. Writers of the jump-target register: one, the immediate (Confirmed).** The only write to R3 on
either path is the site's own `66 03`. Nothing loads R3 from memory, a table, or a variable before the
`jsr`.

**4. Writers of RAM address `0`: none (Confirmed, whole image).**
- IDA xrefs TO `0x0`, `0x1`, `0x2`, `0x3`: **0 each**.
- Whole-image scan for the store-through-zero-base idiom (`mov.l #0,rN` then `[rN]` store): **0 hits**.
- DTBL at `FFED8A34` (3 triples {src,end,dst}): copies to RAM `0x68514`, `0x12570`, `0x1217E` only;
  **none covers `0x0-0x3`**.
- BTBL at `FFED8A58` (3 ranges): `0x12CD8-0x68514`, `0x1230A-0x12570`, `0x4-0x1217E`. Lowest start is
  `0x4`; **`0x0-0x3` is never zeroed**.
- Result: the package never stores anything at `RAM[0]`. The value there on any path is
  power-on-indeterminate. **Unknown**, and it is a deliberate trap, matching doc 127.

**5. Neither site is on a live path (Confirmed in `K7_SUB_FINAL3`; refines doc 127).**
Call graph above both sites, walked to a fixpoint:

    FFEE2220 site: sub_FFEE2208 <- sub_FFEE1958 <- sub_FFF45E0D <-> sub_FFF454C5
                   sub_FFF454C5 <- {dead_FFEE1868, sub_FFF45496, sub_FFF45E90}
                   sub_FFF45496 <- dead_FFEE1780 ;  sub_FFF45E90 <- sub_FFF45496
    FFEE223B site: sub_FFEE2225 <- dead_FFEE19E4

Every root — `dead_FFEE1780`, `dead_FFEE1868`, `dead_FFEE19E4` — has 0 inbound call edges. A whole-image
32-bit-LE pointer scan for any of the ten functions in the chain returned **0 hits** (no vector, no
pointer table). These are CC-RX runtime/stdio library functions (the chain passes through the
`_INITSCT` neighbourhood `FFF45xxx`) that the linker kept but the application never reaches. So the
`jsr 0` is dead library residue, not a live call. This does not change M15's byte accounting (the
bytes stay inside the SUB window as code); it corrects only the "live"/"in the reach mask"
characterisation in doc 127 Open §3.

**6. Vector tables do not target `0` (Confirmed).** Fixed vectors (EXTB `FFFFFF80`, 32 entries) all
point into the `FFF47E3x` dispatch stub; reset (`FFFFFFFC`) = `FFC00000`. None is `0`. The 40 INTB
entries (`FFED8A70`) that read `00000000` are unused interrupt slots (the vector value is the handler
address, left null for unused sources) — they are not a handler at, nor a writer of, RAM `0x0`.

## USB relevance

None. Both sites are dead CC-RX stdio library stubs on the SUB (RX64M) side. They touch no USB
register, no SCI, no DMA, and carry no data path. This lane neither adds to nor subtracts from the USB
findings; it closes an "Unknown" that doc 127 left open.

## Open

1. The exact power-on value at `RAM[0]` is hardware/indeterminate and cannot be read from the image.
   It is Unknown by design; nothing in the package sets it. No further static work can resolve it.
2. The precise CC-RX library identity of `sub_FFEE2208`/`sub_FFEE2225` (char-put vs the simulated-I/O
   console backend) is Inferred from the call shape and the `FFF45xxx` runtime neighbourhood; it does
   not affect the verdict and was not pinned further, since the functions are unreached.

### Corrections to earlier docs (owning docs not edited)

- **Doc 127, Open §3 ("The live `jsr` to address 0").** The bytes and the address-0 conclusion are
  right. The word *live* is not: in `K7_SUB_FINAL3` both sites are reached only through functions with
  0 inbound edges / 0 vectors / 0 pointer hits (`FFEE1780`, `FFEE1868`, `FFEE19E4`), i.e. unreferenced
  CC-RX stdio library code. New basis: whole-image pointer scan 0 hits for all ten chain functions;
  call-graph fixpoint roots are all dead. Byte accounting unchanged.
